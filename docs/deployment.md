# Подготовка к клонированию и первому VPS

Этот документ описывает подготовленный репозиторий. Настройки сервера ещё
не применены, DNS не менялся, рабочая PostgreSQL не открывалась и не мигрировалась.
Шаблоны в `deploy/` требуют реального домена, путей, пользователя и TLS-сертификатов.

## Что исправлено перед клонированием

- Секреты читаются из игнорируемого корневого `.env`, образец — `.env.example`.
- `DEBUG` — настоящий boolean из окружения, по умолчанию `False`.
  Локальный `.env` содержит `DEBUG=True`, поэтому разработка остаётся доступной.
- `ALLOWED_HOSTS` — список доменов без схемы через запятую;
  `CSRF_TRUSTED_ORIGINS` — список полных HTTPS origins. При `DEBUG=False`
  пустой `ALLOWED_HOSTS` блокирует запуск с понятной ошибкой.
- При `DEBUG=False` по умолчанию включаются HTTPS redirect и secure cookies.
  `TRUST_PROXY_HEADERS=True` задают только за Nginx, который перезаписывает
  `X-Forwarded-Proto`, при недоступном извне Gunicorn `127.0.0.1:8000`.
- HSTS изначально равен 0: включать его нужно после проверки HTTPS.
  Для первого этапа можно установить `SECURE_HSTS_SECONDS=3600`, затем увеличить.
  Поддомены и preload не включаются автоматически.
- Django ограничен исправленной веткой 5.2 LTS; Gunicorn — Linux-зависимость.
  Для Pillow и sqlparse заданы исправленные минимумы 13.0.0 и 0.6.0:
  предыдущие версии из lock имели опубликованные security advisories.
  Это уязвимости зависимостей, а не доказанная эксплуатация через данный сайт.
  Окружение воспроизводится из `poetry.lock`, приложение не устанавливается
  как несуществующий пакет `stonecatalog` (`package-mode=false`).
- Requests/BeautifulSoup/Selenium объявлены в отдельной необязательной группе
  `parsers`. Для сайта и CSV-импортёра они не нужны. Старые браузерные парсеры
  дополнительно требуют браузер/драйвер; их запуск на сервере не автоматизирован.
- Tilda CSS/JS/images включены в `collectstatic` с префиксами `legacy/basic/`
  и `legacy/catalog/`. HTML/исходники при этом не публикуются.
  Nginx-шаблон сохраняет `/css/`, `/js/`, `/images/`, `/trend/...`, `/catalog/...`.
- Старый несуществующий `myapp` в обработчике 404 заменён рабочим root handler.
- Восстановлен русский текст 404, сообщений пустого каталога и панели экспорта.
  Ассеты 404 теперь имеют абсолютные URL `/catalog/css/`, `/catalog/js/` и
  `/catalog/images/`, которые не зависят от глубины ошибочного адреса.
- Добавлено совместимое имя `basic_page:productions`: существующее имя
  `production` остаётся. До этого часть шаблонов падала с NoReverseMatch.
- Логи направлены в stderr/stdout; systemd собирает их в journal.

## Очистка

Удалены только пустые неиспользуемые `mysite/s.py` и
`mysite/basic_page/templates/basic_page/export_panel.py` (0 байт каждый).
Они восстановимы из Git. Пустой локальный `db.sqlite3` и Python-кэши можно
удалять: рабочая БД здесь PostgreSQL, а кэши пересоздаются интерпретатором.

Сохранены `__init__.py`, все миграции, исходные Tilda HTML/assets, изображения,
JSON результатов классификации и старые команды. Даже подозрительные `d`/`ult`
содержат действующую логику и потому не удалялись. Их нельзя использовать
как часть деплоя: `ult` массово заменяет цену/толщину акрила, `d` — сертификаты;
`remove_bad_acrylic_images` и некоторые старые парсеры удаляют/заменяют примеры.

В четырёх старых, не подключённых к URL, Tilda-файлах остаётся повреждённый текст:
`front/page45370923.html`, `front/page48404995.html` и их копии в `front/files/`.
Они сохранены как исходные материалы, не включаются в static и не раздаются
через Django. Их восстановление требует исходного текста; значения наугад
не подставлялись. Это не препятствует клонированию/запуску текущих маршрутов.

## Что попадёт в клон

Сначала просмотрите и зафиксируйте текущие изменения, включая новые `docs/`,
`examples/`, `deploy/`, `scripts/`, `.env.example`, env-модуль и тесты.
Проверьте `git status` и `git diff --check`, затем сделайте commit и push
в выбранную ветку. Это не выполнено автоматически. Один `git clone` удалённого
репозитория не забирает локальные изменения и untracked-файлы.

Проверки перед публикацией:

```powershell
poetry check --lock
.\.venv\Scripts\python.exe scripts\check_release.py
git diff --check
git status --short
```

`check_release.py` копирует кандидата релиза (tracked-файлы с текущими правками
и новые неигнорируемые файлы) во временный каталог без `.env`, media и `.venv`.
Запускает там тесты с SQLite/Storage в памяти, проверку миграций, реальный
`collectstatic` и deployment-checks Django на проверочных production-параметрах.
Допускаются только два осознанных предупреждения HSTS `W005`/`W021`:
includeSubDomains/preload оставлены выключенными. Прочие предупреждения — ошибка.
Он не меняет Git и не подключается к рабочей БД. Запускайте его Python-окружением,
в котором установлены main-зависимости из нового lock-файла. Никакого
`git clean -fdx` перед релизом: он удалит локальные `.env` и media.

## Что нужно перенести отдельно

На момент инвентаризации `mysite/media/`: 4291 файл, 6857.53 MiB (около 6.7 GiB).
Это не мусор. Из Git папка исключена и через клон не переносится.
Без чтения БД нельзя определить, какие из этих файлов уже не используются,
поэтому автоматической чистки media не было.

Отдельный перенос:

1. Проверенный dump рабочей PostgreSQL: каталог, примеры, заявки, пользователи,
   группы/права, применённые миграции и остальные таблицы. Размер и версия БД
   пока не проверялись. Нулевой `db.sqlite3` не является резервной копией.
2. Полная папка media с прежними относительными путями. На сервере рекомендуемый
   путь шаблонов — `/srv/kithenstonecatalog/shared/media`, а в `.env`:
   `MEDIA_ROOT=/srv/kithenstonecatalog/shared/media`.
3. Новый серверный `.env`, созданный из `.env.example`. Старые секреты были
   в истории Git: новый `SECRET_KEY` и пароль БД нужны до публичного запуска.
   Приватные ключи/пароли не отправляйте в переписку и не коммитьте.

Не переносите Windows `.venv`, Python-кэши, IDE-настройки и сгенерированный
`staticfiles/`. Статику на сервере заново собирает `collectstatic`.

## Первый клон и установка

Нужен Python 3.13 (по pyproject), PostgreSQL версии, совместимой с Django 5.2
(14+), Nginx, systemd и доступ GitHub по SSH. Команды ниже — инструкция,
а не выполненные операции. Каталог и пользователя сначала создают на VPS.

```sh
git clone git@github.com:Bergenham/kithenstonecatalog.git /srv/kithenstonecatalog/app
cd /srv/kithenstonecatalog/app
python3.13 -m venv .venv
. .venv/bin/activate
python -m pip install 'poetry>=2.4,<3'
poetry install --only main --no-root
cp .env.example .env
chmod 600 .env
# Заполнить .env: новые секреты, БД, домены, MEDIA_ROOT.
# После настройки закрытого upstream и Nginx: TRUST_PROXY_HEADERS=True.
python scripts/check_release.py
cd mysite
python manage.py collectstatic --noinput
```

Для дополнительных старых импортёров отдельно: `poetry install --with parsers`.
Проверка изолированного релиза не доказывает соединение с реальной PostgreSQL
или доступность HTTPS — это проверяется уже на сервере.

## После клонирования: последовательность

1. Создать непривилегированного пользователя, закрыть внешний доступ к PostgreSQL
   и порту Gunicorn, подготовить Python 3.13 и main-зависимости.
2. Подготовить новую БД и восстановить резервную копию; сверить количество
   камней, примеров, заявок и пользователей. Не импортировать DEMO-пакет в рабочий
   каталог и не запускать старые парсеры для «воссоздания» существующей БД.
3. Перенести media с сохранением путей/прав. Пользователь приложения должен
   писать в media, Nginx — читать. Исходники и `.env` не должны раздаваться вебом.
4. Проверить `migrate --plan`. Миграция 0015 нужна импортёру; если 0013/0014 ещё
   не применены, они тоже войдут в план. Применять только после проверенного
   backup и проверки восстановления на отдельной БД.
5. Собрать static, адаптировать `deploy/stonecatalog.service.example`
   и `deploy/nginx.conf.example`. В systemd пути и пользователь должны реально
   существовать. Шаблон `ReadWritePaths` рассчитан на внешний shared/media.
6. Выпустить сертификат через временную HTTP-конфигурацию и только затем
   включать HTTPS-блок Nginx. Проверить `nginx -t`, затем localhost Gunicorn,
   HTTPS страницы/статику/media, login admin, CSRF POST формы и создание заявки.
   Новый Django `SECRET_KEY` завершит старые подписанные сессии/токены.
7. Проверить `manage.py check --deploy` с настоящим `.env`. Предупреждение HSTS
   ожидаемо до его осознанного включения. Настроить регулярный backup БД и media,
   срок хранения, журналы и уведомление о недоступности сайта.
8. Если домен обслуживает старый сайт, выполнить финальную синхронизацию данных
   и согласованное переключение DNS с возможностью отката.

Linux/systemd/Nginx и реальная PostgreSQL в Windows-проверках не запускались.
Шаблоны надо проверить на выбранной ОС перед включением сервиса.

## Что требуется от владельца

- IP VPS, провайдер, ОС/версия, CPU/RAM, объём свободного диска, наличие других
  сайтов/панели управления на этом VPS. Помимо 6.7 GiB media нужны место БД,
  временных копий и резервных копий; размер БД ещё неизвестен.
- SSH-пользователь и возможность `sudo`; доступ лучше настроить по публичному
  ключу. На GitHub — read-only deploy key для клонирования приватного репозитория.
- Основной домен, нужен ли `www`, доступ к DNS, есть ли CDN/Cloudflare, где сейчас
  работает сайт и допустимо ли окно недоступности.
- Откуда берём рабочую PostgreSQL и media, версия PostgreSQL, как получить
  согласованный backup. Решение: переносим текущие данные или запускаем пустую БД.
- Выбранная ветка/коммит для деплоя после commit/push подготовленных изменений.
- Новые секреты, созданные на сервере; нужен ли OpenAI API для классификации.
- Куда хранить backups и куда отправлять уведомления об ошибках.

## Операции с риском данных/простоя

- `migrate`, `pg_restore`, смена паролей/секретов и неверный `MEDIA_ROOT`.
- `git clean -fdx`, рекурсивное удаление media, `collectstatic --clear` по
  неверно заданному STATIC_ROOT. В этой подготовке такие команды не запускались.
- Старые нормализаторы/парсеры, удаляющие примеры или массово меняющие цены.
- Перезапуск/reload Nginx/systemd с непроверенной конфигурацией и переключение DNS.
- HSTS до готового HTTPS; includeSubDomains/preload без проверки всех поддоменов.
