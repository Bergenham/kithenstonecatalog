# Пакетный импорт каталога

Команда использует реальные модели приложения `catalog`: `Stone` с multi-table
наследниками `QuartzStone`, `AcrylicStone`, `NaturalStone`, `CeramicsStone`.
Единственное превью — поле `Stone.priview_img` (орфография существующего поля
сохранена). Примеры — `StoneImage.image`, FK `StoneImage.stone`, обратная связь
`example_images`. У примера нет названия, подписи или сортировки: таких колонок
в CSV нет. Лимит 10 в admin inline не является ограничением БД; импорт не
ограничивает число примеров на камень, кроме общего лимита размера пакета.

## Миграция

Добавлена `catalog/0015_stoneimage_import_id`: nullable unique `StoneImage.import_id`,
до 100 символов. Существующие строки остаются с NULL, их изображения и связи
не меняются. Это необходимо, потому что ни имя файла, ни PK не являются удобным
стабильным внешним ключом примера. Колонка `example_id` записывается в `import_id`.
Новых сущностей и бинарных полей БД нет. В Storage хранятся изображения,
в PostgreSQL — их имена и связи.

Миграция подготовлена, но не применена к рабочей/production-БД. Перед первым
использованием команды примените её в выбранной среде в согласованное окно:

```powershell
cd D:\Project.com\kithenstonecatalog-main\mysite
..\.venv\Scripts\python.exe manage.py migrate catalog
```

Эта команда применит также ещё не применённые предшествующие миграции каталога,
включая 0013/0014. Сначала проверьте план миграций и резервную копию в вашей среде.
Построение уникального индекса может кратковременно блокировать запись
в `catalog_stoneimage`; это важно для большой таблицы.

## Файлы пакета

Готовый пример находится в `examples/catalog_bundle/`:

```text
catalog_bundle/
  entities.csv
  examples.csv
  images/
    entity_001/
      preview.jpg
      example_01.jpg
      example_02.png
    entity_002/
      preview.webp
      example_01.jpg
```

В нём два демонстрационных камня и три примера. Изображения — небольшие цветные
образцы с надписью DEMO, не реальные товары. Они воспроизводятся командой
`python examples/generate_catalog_demo_images.py` из корня репозитория.

Оба CSV обязательны. Пустой файл только с заголовком допустим: так можно
импортировать только примеры к существующим камням или только камни.
Кодировка UTF-8, допускается BOM Excel. Разделитель — запятая; для Excel-файла
с точкой с запятой укажите `--delimiter ';'`. Значения с запятыми/переносами строк
заключайте в двойные кавычки по правилам CSV. Заголовки чувствительны к регистру.
Неизвестные/повторяющиеся колонки и строки с неверным числом колонок — ошибки.

### entities.csv

Минимальный формат (все четыре колонки и значения обязательны на каждом запуске):

```csv
entity_type,article,name_stone,preview
quartz,DEMO-Q-001,Demo Quartz White,images/entity_001/preview.jpg
```

| Колонка | Значение |
| --- | --- |
| `entity_type` | `quartz`, `acrylic`, `natural`, `ceramics`; определяет модель и `material` |
| `article` | Уникальный артикул `Stone.article`, до 100 символов; стабильный ключ объекта |
| `name_stone` | Название 5–50 символов, по существующему валидатору модели |
| `preview` | Относительный путь к обязательному изображению |
| `abt_prise` | Необязательная цена: 100–9999999.99, до двух знаков после точки |
| `country` | Необязательное значение choices `Stone.CountryChoices`, например `Чехия` |
| `thickness` | Необязательное целое 0–9999, миллиметры; существующий валидатор модели |
| `about_brand` | Необязательный текст |
| `archive` | Если колонка присутствует: `true`, `false`, `1`, `0`; пустое значение — ошибка |
| `brand_stone`, `color`, `texture`, `faktura`, `link_serf` | Необязательные точные значения choices соответствующего дочернего типа |

Для choices указывайте хранимые значения, не произвольные подписи. Например,
`AcrylicStone.faktura`: `silky`, а не `Шелковистая`; у натурального камня
`brand_stone`: `n_stone`, а не `NatureStone`. `link_serf` — значение существующего
перечисления сертификатов, а не любая ссылка. Источник допустимых значений —
`catalog/models.py`; `full_clean()` выполняется и при dry-run, и при импорте.

У существующего объекта дополнительные колонки, отсутствующие в заголовке CSV,
сохраняются. Пустое значение присутствующей nullable-колонки явно очищает её
в NULL. Для нового объекта отсутствующие дополнительные колонки получают
существующие defaults модели. Внешние пробелы значений обрезаются.

Артикулы сравниваются точно, с учётом регистра. Смена `entity_type` существующего
артикула и неоднозначное multi-table наследование отклоняются. Если нужно
переименовать сам стабильный артикул, это отдельная операция: новое значение
будет расценено как новый объект. Камень без артикула не сопоставляется по
названию/изображению и автоматически не объединяется.

### examples.csv

```csv
example_id,article,image
DEMO-Q-001-kitchen,DEMO-Q-001,images/entity_001/example_01.jpg
DEMO-Q-001-bathroom,DEMO-Q-001,images/entity_001/example_02.png
```

Все три значения обязательны. `example_id` — уникальный во всём каталоге
стабильный идентификатор до 100 символов. Он не зависит от имени файла: смена
пути или содержимого `image` обновляет тот же пример. Привязка идентификатора
к другому камню запрещена. `article` должен присутствовать в `entities.csv`
или уже существовать в БД. Старые примеры с NULL `import_id` сохраняются;
автоматического сопоставления по имени/содержимому нет. Для управления таким
старым примером нужно отдельно назначить ему уникальный `import_id`; иначе
новый `example_id` создаст новый пример.

## Запуск

Из каталога `mysite/`, в среде с применённой 0015:

```powershell
..\.venv\Scripts\python.exe manage.py import_catalog ..\examples\catalog_bundle --dry-run
..\.venv\Scripts\python.exe manage.py import_catalog ..\examples\catalog_bundle
```

Linux, также из `mysite/`:

```sh
../.venv/bin/python manage.py import_catalog ../examples/catalog_bundle --dry-run
../.venv/bin/python manage.py import_catalog ../examples/catalog_bundle
```

Dry-run читает БД и Storage для проверки существующих объектов и сравнения SHA-256,
но не пишет туда. Проверенные изображения временно копируются в системный
временный каталог, удаляемый после команды. План dry-run может измениться,
если кто-то поменяет каталог до реального импорта.

Обычный запуск сначала валидирует весь пакет, затем сохраняет его в одной
транзакции. Любая ошибочная строка отменяет весь пакет; частичного импорта нет.
Команда сообщает CSV и номер строки, завершает работу с ненулевым кодом.
При успехе показывает отдельно созданные, обновлённые, неизменённые камни и
примеры. При откате создано/обновлено = 0; счётчик ошибок включает ошибочные
строки, файловые/операционные ошибки и ошибки очистки.
Если результат COMMIT нельзя подтвердить, вместо нулевых счётчиков выводится
сообщение о необходимости проверить результат фиксации в БД.

Повторный запуск неизменённого пакета не добавляет ни записей, ни файлов:
содержимое изображений сравнивается по SHA-256, а не только по пути пакета.
Не удаляются камни/примеры, отсутствующие в новом пакете. Для PostgreSQL
транзакционная advisory lock сериализует реальные запуски этой команды;
существующие записи блокируются `select_for_update`. Это не блокирует все
сторонние редакторы: конфликт уникальности с ними приведёт к безопасной отмене.
Не вызывайте импортёр внутри внешнего `transaction.atomic()`.

## Безопасность изображений и файловое хранилище

- Пути относительны корню пакета, разделитель `/`, без `..`, `.`, абсолютных
  путей, Windows-дисков/UNC/ADS, обратных слешей и управляющих символов.
- Символические ссылки и Windows junction запрещены, результирующий путь
  проверяется на принадлежность пакету. Не изменяйте пакет во время проверки
  или копирования; команда предназначена для локально подготовленного каталога,
  а не для обработки распаковываемого параллельно недоверенного архива.
- Разрешены только JPEG (`.jpg`, `.jpeg`), PNG, WebP, с совпадением расширения
  и декодируемого Pillow формата. SVG/GIF/HTML, анимация и повреждённые файлы
  отклоняются. Выполняются проверка структуры и полное декодирование.
- Лимиты: 20 MiB на изображение, 512 MiB суммарно для уникальных путей картинок,
  40 мегапикселей на изображение, 5 MiB и 10000 строк на каждый CSV.
- Новые файлы сохраняются через Storage полей с их существующими `upload_to`,
  под случайными UUID-именами. `.path` backend не требуется; поддерживаются
  файловое и удалённое хранилища с обычным контрактом `save/open/delete/exists`.
- При обычной ошибке или Ctrl+C транзакция откатывается; новые файлы удаляются.
  Если Storage.delete недоступен, команда печатает точные имена оставшихся файлов.
  Перед удалением проверяются ссылки БД: уже связанный файл или файл, чьи ссылки
  нельзя проверить из-за недоступности БД, сохраняется с предупреждением.
  Storage backend должен корректно возвращать итоговое имя из `save` и не менять
  имя/содержимое чужого объекта перед исключением.
- Старые файлы при успешной замене намеренно сохраняются: они могут быть общими
  или нужны для восстановления. Неиспользуемые старые файлы можно удалять
  отдельной процедурой только после проверки ссылок и резервной копии.
- При SIGKILL, выключении машины или обрыве связи во время COMMIT нельзя
  гарантировать согласованность БД/Storage средствами одной Django-транзакции.
  Возможны новые файлы без ссылок; перед очисткой нужно сверить имена со всеми
  полями изображений БД. Существующие файлы импортёр не перезаписывает.

## Проверки

Тестовая конфигурация `mysite.import_test_settings` использует только отдельную
SQLite-БД в памяти и `InMemoryStorage`, без подключения к настроенному PostgreSQL
и без записи в существующий media. Миграции выполняются лишь в этой временной БД.

```powershell
cd mysite
..\.venv\Scripts\python.exe manage.py test --settings=mysite.import_test_settings
..\.venv\Scripts\python.exe manage.py makemigrations --check --dry-run --settings=mysite.import_test_settings
```

Это проверяет сценарии импорта и реальную цепочку миграций, но не заменяет
staging-тест на PostgreSQL с целевым Storage (включая advisory lock, параллельный
запуск двух команд и доступность удаления файлов). Для staging сначала сделайте
dry-run примера; затем импортируйте его дважды и проверьте неизменность счётчиков.
